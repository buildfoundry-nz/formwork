# Security policy

## Reporting a vulnerability

**Please do not open a public issue for a security report.**

Use GitHub's private vulnerability reporting on this repository:
**Security → Report a vulnerability**. It creates a private thread visible only
to the maintainers, and it is the preferred channel because it keeps the report,
the fix, and the advisory in one place.

What helps most in a report: the version (`formwork version`), the smallest
config and tree that reproduces it, what you expected, and what happened.
A proof-of-concept rule file is worth more than a paragraph of description.

### What to expect

| | |
|---|---|
| Acknowledgement | within 5 business days |
| Initial assessment | within 10 business days |
| Fix or mitigation plan | communicated with the assessment |

This is a small project with a single maintainer. Those numbers are what we
intend to hold to, not an SLA — if a deadline slips you will hear why rather
than hear nothing.

We will credit you in the advisory unless you would rather we didn't. If you
plan to disclose publicly, tell us your timeline and we will work to it.

## Supported versions

While at 0.x, **only the latest release** receives security fixes. There are no
maintained release branches. See [VERSIONING.md](VERSIONING.md).

## Threat model — read this before reporting

formwork is a guardrail engine that runs in CI and in git hooks. Two properties
of its design are deliberate and are *not* vulnerabilities, though they shape
what is:

### 1. Rule configuration is code

The `command:` and `git-diff:` rule types execute external programs. The command
line comes from the repository's own tracked YAML under `.formwork/`, and
formwork runs it with the privileges of whoever invoked formwork.

**This is the intended design** — the escape hatch exists so a repo can keep a
check the declarative rule types cannot express. It also means:

> Anyone who can merge a change to `.formwork/` can execute arbitrary code in
> your CI and on the machine of every developer with hooks installed.

Treat `.formwork/` with the same review bar as your CI workflow definitions,
because it has the same power. `formwork lint` enumerates every `command` rule
precisely so this surface is visible rather than discovered. That enumeration
covers **rules**; it does not cover the hook shims described in §3, which are the
other executable content under `.formwork/`.

A report that "a malicious `.formwork/rules/*.yaml` can run a command" describes
the documented feature. A report that formwork executes something **not**
declared in tracked config, or that a `command` rule escapes the enumeration
`lint` performs, is a real finding.

### 2. formwork modifies git configuration when asked

`formwork hooks install` points `core.hooksPath` at a formwork-managed directory
and writes shim scripts there. It is an explicit, opt-in command. Doing this
without being asked, or writing outside that directory, would be a finding.

### 3. The hook shims are tracked shell scripts, and `lint` does not enumerate them

`formwork hooks install` writes one shim per git-hook lane into
`.formwork/hooks/`. Their content depends on nothing but the lane name, so they
are meant to be **committed and shared** — every clone then gets the same wiring
instead of depending on each developer having run install. That makes them the
one executable surface under `.formwork/` that `formwork lint` does not report:
`lint` reads rules, and a shim is not a rule. Once they are tracked, a change to
`.formwork/hooks/` arriving in a `git pull` replaces a script that runs on your
next commit — in a directory reviewers do not habitually read.

What limits that today, stated exactly:

- The generated content is fixed and machine-independent — `#!/bin/sh`, a
  `# generated by 'formwork hooks install'` marker, and
  `exec formwork check --lane <lane> [--staged]`. Anything else in one of those
  files was not written by `hooks install`, so a diff of `.formwork/hooks/` is
  short and worth reading in full.
- `formwork hooks verify` compares each expected shim **byte for byte** against
  the text `hooks install` would generate, at the directory git itself reports it
  will run hooks from, and reports the file unless it is a regular, executable,
  identical file. Any edit to a shim is therefore rejected, including one that
  leaves the `exec` line textually present but unreachable. It also names files
  in that directory git would execute and the config does not declare, and the
  hooks `core.hooksPath` is currently shadowing.
- `formwork hooks install` **refuses to take over hook wiring this project
  already has**, so running it can never silently disarm a gate somebody else
  set up. A `core.hooksPath` this repository declares — in its local config, in
  its worktree config, or resolved through an `include.path` directive — and
  hooks git is already running out of its default `.git/hooks` directory are
  each exit 2 that writes nothing, printing the `formwork check --lane <lane>
  --staged` line to add to the hook already in charge. There is no flag for any
  of them: whose hooks run is the project's decision, not formwork's. The single
  refusal with an escape is a setting *wider* than this repository, such as a
  machine-wide hook runner in a global config — a default rather than a decision
  this repository made — which `--override-global` clears here and only here.
  Issue #146.

One limit, stated exactly, because it bounds what that check is worth:

- **Verify is not a substitute for reading the diff.** It runs when someone runs
  it. A shim arriving in a `git pull` runs on the next commit whether or not
  anyone verified afterwards.

Review `.formwork/hooks/` the way you review `.formwork/rules/`. A report that
`hooks install` writes anything other than the content above, that it takes over
wiring this project had already declared, or that `hooks verify` certifies
wiring git will not execute, is a real finding.

## What we consider a vulnerability

Highest priority, and the class this project actively hunts:

- **A fail-open.** Any path where formwork exits `0` when it owed a `1` or `2`
  — a rule that silently doesn't run, a file silently not scanned, an error
  swallowed into a no-match, an exemption applying wider than declared, a check
  that passes vacuously over an empty set. This is the defect class the codebase
  is organized around, and a report of one is welcome even if you cannot show
  malicious exploitation: in a guardrail engine, a check that quietly stops
  checking *is* the security failure.
- **Exemption or suppression bypass** — making a finding disappear without an
  enumerated, auditable escape hatch.
- Sandbox or path escapes: a rule reading or writing outside the repository
  root, or path traversal through config-supplied globs.
- Crashes reachable from untrusted repository *content* (as opposed to
  untrusted config) — a malformed source file, SQL, or filename that panics the
  engine, or a pathological regex causing unbounded resource use during a scan.
- Vulnerabilities in the dependencies we bundle into released binaries, where
  formwork's use of them is reachable.

## What is out of scope

- Arbitrary execution via `command:` rules in config you control (see above).
- Denial of service from a config deliberately written to be pathological.
- Findings that require an attacker to already have commit access to
  `.formwork/`, unless the impact exceeds what that access already grants.
- Reports against unreleased builds, or against `internal/` used as a library —
  there is no supported Go API surface.
- Automated scanner output with no analysis of reachability in this codebase.

## Verifying what you run

Releases are static binaries published as GitHub Releases with a
`checksums.txt`. Verify the checksum of anything you install, and pin an exact
version rather than tracking latest. `formwork version` reports the tag the
binary was stamped with; a binary that is not a real tagged release cannot
satisfy an `engine:` constraint, by design.
